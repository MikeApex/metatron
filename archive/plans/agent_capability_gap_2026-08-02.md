# Agent Capability Gap — What Agents Are Told They Have vs. What Exists

*Written 2026-08-02, out of the SEQ 021 troubleshoot. Scope: every agent, not just Logistics.*
*Status: **survey and proposal only**. No agent files edited — `config/agents/*.md` are frozen post-review; per `parallel_chats_index_2026-06-11.md` rule 3, audit work proposes and never edits.*

---

## Why this exists

On 2026-08-02 the user asked Logistics for a recurring monthly reminder to pay credit card bills. Logistics spent three of six turns guessing the parameters of a tool it had been told to use, never saved anything, and the Synthesizer told the user *"The reminder for the 15th is set."* It was not.

Two of the three causes were code-level and are fixed (see "Already fixed" below). The third is not a bug — it is a **standing mismatch between what agent instruction files promise and what the system can actually do.** This document inventories that mismatch.

**The deliberate framing:** this is a list of what to *build*, not what to *remove* from the agent files. With a calendar arriving shortly, narrowing Logistics' instructions to match today's thin capability would be the wrong move — it would have to be undone in a fortnight. Everything below is phrased as a gap to close.

---

## The three kinds of gap

Plain-language version first, then the precise definition.

1. **Told-but-not-offered.** The instruction file tells the agent to use a tool, but that tool is not on the agent's advertised list. *Technically:* the tool name appears in `config/agents/{agent}.md` but not in that agent's `allowed_tools` in `config/modules/routing_cloud.yaml`, so it is filtered out of `tool_schemas` before the model ever sees it.

2. **Told-but-nonexistent.** The instruction file names a tool that was never built. *Technically:* the name appears in the agent file but in no `tools/*.py` module and not in `register_tools()`.

3. **Offered-but-inert.** The tool exists and is advertised, but cannot do anything because its backing service is unconfigured or its target is not writable. *Technically:* the handler runs and returns an error or a no-op — e.g. CalDAV with `enabled: false`.

---

## Finding 0 — the whitelist does not actually restrict anything (security-relevant)

**Plain:** Each agent has a list of tools it is supposed to be limited to. That list controls what the agent is *shown*, but not what it is *allowed to run*. If an agent asks for a tool that isn't on its list, the system runs it anyway.

**Technical:** In `core/orchestrator.py → _run_single_agent()`, the per-agent whitelist filters `tool_schemas` only:

```python
allowed = get_allowed_tools(agent_name)
if allowed is not None:
    allowed_set = set(allowed)
    tool_schemas = [s for s in tool_schemas if s["name"] in allowed_set]
```

`tool_handlers` is passed to the session loop **unfiltered**, and `dispatch_tool()` looks up `handlers[name]` with no whitelist check. Any agent can invoke any of the 43 registered tools by emitting the call.

**Evidence this is live, not theoretical:** `logistics` is not granted `write_agent_config` in `routing_cloud.yaml` (its list is `read_log, write_log, read_calendar, write_calendar_event`). In the SEQ 021 production trace it called `write_agent_config` three times and the dispatcher executed each one — the failures were signature errors, not permission denials. Its instruction file told it to, so it did, and nothing stopped it.

**Implication.** Every "told-but-not-offered" row below is currently *working by accident* — the agent is not shown the tool, guesses at it from its instructions, and the dispatcher obliges. Closing Finding 0 (Track B / B2, principle of least privilege) without first fixing the allowlists **will break all of them at once.** Sequence matters: fix the lists, then enforce them.

## Finding 3 — offered-but-inert: there is no way to actually set a reminder

**This is the gap that produced the original complaint, and it is the most important item here.**

**Plain:** Logistics is the agent responsible for reminders. It currently has no mechanism to cause anything to happen at a future time. It can write a note saying a reminder exists. Nothing will ever fire.

**Technical — all three candidate paths are closed:**

1. **`write_calendar_event` (advertised to Logistics).** Backed by CalDAV in `tools/caldav.py`. `config/personas/mike/caldav.yaml` has `enabled: false` and an empty `auth.password`, so every call returns the "not configured" error. **This is the one your incoming calendar work will open.**
2. **The scheduler.** `config/personas/mike/scheduler.yaml` holds five hand-written recurring jobs (`morning_brief`, `companion_checkin`, `evening_close`, `weekly_pattern_miner`, `weekly_physical_review`, `ambient_refresh`). They are static and read at daemon start. **There is no tool that can add, edit or remove a job**, so an agent cannot schedule a one-off or a new recurrence.
3. **`write_config`.** Restricted by allowlist to `mission.md` and `prime_directive.md`. In the local validation run Logistics tried exactly this — `write_config(filename="scheduler.yaml", ...)` with a cron expression — and was correctly refused.

So a reminder request can currently be *recorded* (`write_agent_config` → `recurring_obligations`) but never *delivered*. The nearest thing to delivery is the horizon scan in `logistics.md`, which surfaces upcoming items only if a session happens to run and the Coordinator happens to route to Logistics.

**What to build (in dependency order):**

| # | Item | Notes |
|---|---|---|
| 3a | **Enable CalDAV** — fill `auth.password` (Google app password), set `enabled: true`, copy to VM (gitignored, `deploy.sh` will not carry it) | Unblocks `write_calendar_event`, already advertised. Smallest step to a working reminder. |
| 3b | **`read_agent_config` / `write_agent_config` for Logistics** | So the recurring-obligation calendar has somewhere legitimate to live. Currently works only via Finding 0. |
| 3c | **Scheduler-write tool** — `write_schedule(name, when, prompt, notification)` + `list_schedules` / `delete_schedule` | The real fix for "strong reminder." Needs the daemon to reload `scheduler.yaml` on change, or a separate agent-owned job file so hand-written and agent-written jobs don't collide. |
| 3d | **Decide delivery semantics** | The Synthesizer asked the user whether to deliver by calendar alert or in-chat. That choice should be stored (`write_agent_config` → `reminder_preferences`) and honoured, not re-asked. |

Note 3c is the item that makes the promise in `logistics.md` true. 3a alone gives a calendar entry, which may be enough for the credit-card case but does not cover reminders with no natural calendar home.

## Finding 4 — the tool description points at a pre-persona path

`WRITE_AGENT_CONFIG_SCHEMA` in `tools/agent_config.py` describes the store as `data/config/{agent_name}.json`. Since persona unification (2026-07-28) the real path is `data/personas/{persona}/config/{agent_name}.json`. Cosmetic — the model never uses the path — but it is the kind of stale detail that misleads a future reader. Same class as the `/metatron-troubleshoot` stale paths already logged in `SESSION.md`.

## Proposed agent-file edits (NOT applied — files are frozen)

For whoever lifts the freeze:

1. **`logistics.md` lines ~45 and ~111** — the phrase "All baseline data must be written to `write_agent_config`" and "Keep the recurring obligation calendar current" should state the store's actual shape: one labelled key at a time, structured values passed as a JSON-encoded string. Suggested wording, kept short per the SEQ 002 precedent on token-light agent files:
   > `write_agent_config` takes one `key` and one `value` at a time. For structured values (lists, objects) pass the value JSON-encoded as a string — e.g. `key: "recurring_obligations"`, `value: "[{\"day\": 15, ...}]"`.
2. **`synthesizer.md`** — add a line handling the new `[TOOL FAILURES]` block that specialists now append (see below): never report an action as done when it appears there; tell the user plainly what did not save.
3. **All nine specialists** — remove `run_subagent` references; the recursion guard makes them dead instructions.
4. **`physical_health.md`** — remove `get_environmental_snapshot` or build it.

## Already fixed this session (code, not agent files)

Landed in `core/orchestrator.py` + `tools/ambient.py`, validated locally against `sarah_chen`:

1. **Specialists now receive the system clock.** New `clock_line()` / `tools.ambient.current_clock_line()`, injected into the specialist branch of `_run_single_agent()` via the user message (keeps the cacheable system prefix stable). Fixes Logistics inventing `log_date: 2025-05-22`.
2. **Tool errors now name the correct parameters.** `dispatch_tool()` binds with `inspect.signature().bind()` before calling and returns `Correct usage: write_agent_config(required: agent_name, key, value)` on a mismatch. **Measured effect:** the same request that previously failed three times and gave up now self-corrects on the second attempt and saves successfully.
3. **Unrecovered tool failures are reported upward.** `_failed_tool_calls()` appends a `[TOOL FAILURES — these actions did NOT complete]` block to specialist output. Tools that failed then succeeded on retry are deliberately excluded, so a recovered error does not produce a false "it didn't save."
4. **Junk log removed** — the hallucinated `data/personas/mike/logs/2025-05-22.json` moved to `data/diagnostics/bogus_logs/`. Contained only the bogus entry; no real data lost.

**Note for A8 (pre-Alpha refactor):** `clock_line()` and `load_recent_context()` belong with the config concern and will move to `core/config.py`; `dispatch_tool()`, `_signature_hint()` and `_failed_tool_calls()` belong to the tool concern and will move to `core/tools.py`.
