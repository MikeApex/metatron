## Findings

**1. HIGH — A task that has started jumps forward every time its plan is read, and the nudge/check for it is never fired.** tools/day_plan.py:1047, :1062-1063, :920.
`_build` moves a block to `history` when it has *started* (`s < plan_start`), not when it has ended; `_suggestions` skips history blocks; and `placeable` re-places an essential ref whose block is in history and not yet done. Constructed run (vital deadline placed 08:25–08:55; essential): at 08:26 a read makes it history and places a second copy at 08:55; at 08:56 a third at 09:25; the `nudge` and `check` suggestions move with it. `nudge_tick` calls `current()` before reading suggestions, so the rebuild always runs first — three ticks (start+1, end+1, end+10) produced **zero wakes**. What the user sees: in Stage A's Today panel the task they are doing now appears twice (its real slot and a copy half an hour later) and hops every 30 minutes; in Stage B Synth's block reads "Now: X (until 08:55) → Next: 08:55 X", and Mike's Q8/F2 completion checks never reach the wake-and-decide path. The tests miss it because the only nudge exercised is the travel nudge (a skeleton block, rebuilt in place), and "an essential block passing undone reshuffles once" is guarded by `if first.get("essential")` and an `or`. Smallest fix: in `_build`, re-place an essential ref only when **every** history block of that ref has *ended* (`e <= now`), not started; in `_suggestions`, emit the `check` for history task blocks too (the tick's `handled` map already dedupes) and keep the start-nudge for non-history only. Then re-run the three-tick scenario and assert one wake at end+1.

**2. HIGH — A twice-daily medication's second dose disappears from the plan the moment the first is recorded.** tools/day_plan.py:1062-1063, :1004-1005, :549-551.
`placeable` excludes a ref already in history unless `essential and not _ref_done(ref)`, and `_ref_done` tests copy 0 only (`done > 0`). Constructed run (`Take the tablets`, `every=day, times=2`): first build places 08:00 and 11:00; record the 08:00 dose done; the next read returns a plan with **no future dose, no nudge, no check, nothing under unplaced**. The converse (first dose passed, not recorded) places *two* new copies plus the history one — three blocks for two doses — because `copies = target − done` but `_fill`'s counts start at zero and ignore history. Medication is the one category the spec marks always-essential (F10, ROADMAP § 0 clause 8). Smallest fix: for a ref with `copies` derived from `times > 1`, never apply the `had` exclusion (its `copies` already equals the remaining doses), and seed `_fill`'s `counts[ref]` with the number of history blocks for that ref so copy indices continue and `_status_of(ref, copy)` maps `done > copy` correctly.

**3. MEDIUM — A break is laid over a meeting; the code plan then fails its own validator and is still shown.** tools/day_plan.py:770-775.
`put()` places the post-run break at `j` without checking the slots are free. Constructed run: 90-min work task 09:00–10:30 against a 10:30 stand-up → `break 10:30–10:40` overlapping `Stand-up`, `failures: ['V1: break… overlaps event…']`, plan written and rendered (code plans are only logged, never rejected). The user sees a break during their meeting; the Stage B smoke test's "validator clean each run" would fail for a code-side reason. Related noise: after bedtime every unplaced vital item carries reason `outside waking hours` (:844), which V7 (:899-905) does not accept, so V7 fails on every late-evening build. Smallest fix: in `put()`, place the break only if those `brk` slots are not busy/protected (else fall back to the transition gap); have V7 accept `outside waking hours` as a reported reason.

**4. MEDIUM — `note_calendar_write` has no caller: the "my 3pm got cancelled" same-reply repair is dead code, and the Today panel lags a Metatron calendar write by up to 10 minutes.** tools/day_plan.py:356; plan A5 lists "`tools/caldav.py` (3 lines)" — `git diff --stat` shows no caldav.py change, and `grep -rn note_calendar_write` finds only the definition and the test. So `calendar_dirty` is never set and the boxed fetch never runs. The test "a turn that wrote the calendar re-fetches inside the 3 s box" calls the hook directly and so passes with nothing wired. Smallest fix: one `day_plan.note_calendar_write()` call (in a try/except) at the success exit of `write_calendar_event`, `update_calendar_event`, `delete_calendar_event` (tools/caldav.py:853, 1118, 1285), plus a source pin in the wiring test.

**5. LOW — Return travel after a located appointment is not built.** tools/day_plan.py:647-667. § 5.3 says "and back, when the next block is elsewhere or home"; only outbound travel exists. After Physio 14:00–15:00 at Harley St the fill can start a task at 15:00 as if the user were home. Stage A acceptance ("tasks ordered sensibly") will show it.

**6. LOW — Google Routes is called synchronously inside the `/plan/today` poll.** tools/day_plan.py:1183, :1357. `today_view` → `current(for_reply=False)` → `allow_lookup=True`, so a rebuild on the poll waits on an HTTP call (`TIMEOUT_SECONDS = 10`) per uncached (origin, destination, hour). The module's own rule 3 says a poll never waits on a route lookup; cached and capped, so it is bounded, but the test "never made on the reply path" does not cover the poll.

**7. LOW — Two Stage B details that will read as failures later.** (a) `request_replan`'s force does not survive to the model: `current()` writes `pending` without a `force` key (:1200) while `start_reshuffle` honours `pend.get("force")` (:1623), so a replan inside the 15-min gap gets only the code rebuild though the tool reply promises a rework. (b) `rhythm_offer(mark=True)` takes the **blocking** plan lock on the reply path (:1455-1458) and reads 14 conversation files per user turn until a boundary is set — contrary to the non-blocking rule for replies; rare, but it is the one blocking lock on that path.

**8. LOW — The hidden ledger actions leak through the error text in Stage A.** tools/obligations.py:1419-1423. `update_task`'s "must be one of …" error now lists `link_goal, set_priority, set_stakes, set_zone, day_starts`, so a model that mis-types an action is told about the Stage B actions and the handler will accept them. The schema is clean (R1-1 holds); this is the one remaining surface.

Not findings, checked and fine: the day boundary is routed through every stamp consumer I could enumerate (`_one_off_row`, `_recent_close_match`, `_source_duplicate`, `_raised_today`, `note_raised`, `sweep`, `_recently_closed`, `consult_index`, `accountability_items`); stated-vs-inferred refusal; `is_essential` precedence; unconfirmed/lapsed semantics and adherence denominators; location proposals (keyed `zone@date`, closed under `_user_act` with location evidence, no-`source` proposals unchanged); flock held for file I/O only with no nesting; every spawned thread binds `persona_scope`; reply-path lock is non-blocking (except 7b); the client's `message` handler already honours `proactive`; the location default is adopted only on an explicit `true` with nothing stored.

**Verdict:** two high findings in `tools/day_plan.py` (`_build`'s started-vs-ended history rule and its multi-dose handling) make the plan wrong for the user's current task and for twice-daily medication; fix those, wire the caldav hook, and the Stage A claim otherwise stands.
